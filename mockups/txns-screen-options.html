The Transactions screen, three ways

This is the agent screen that goes dark when the switch flips. It is drawn as a SkySlope import inbox, and there is no table behind it: the importer that would fill it is still index.ts.pending, and its decisions save to the browser only. So the question is not how to unstub it, it is what the screen should be.

Counts are the live book read today: 80 transactions across 8 agents. net_commission is set on 0 of 80, client_name on 2, effective_date on 1, contract_type on 1, external_id on 0. Addresses and client names are a middle dot because this repository is public.

One.Your files, as a list

Drop the inbox idea. The screen becomes the agent's own transactions, read from realty_transactions, which Deals already loads, grouped by what happened to the deal. This is closest to what agents have on the old Hub today through tx-list, so nobody loses anything on switch day. It needs no new table and no new column. What it gives up is the confirm step: nothing asks the agent whether the file is really theirs.

Two.Keep the confirm step, move it off the browser

Keep what the screen was for. The broker imports the week's files, each one waits on the agent to accept it, send it back with a correction, or say it is not theirs. Same cards, same three actions, but the decision writes to a column on realty_transactions instead of to that browser, so it survives a different phone and the broker can see who has not answered. Costs one column and a small write path.

Three.Stay an import inbox, and say what it is waiting on

Leave the screen's purpose alone and replace the coming soon card with a real readiness panel: what the inbox needs, which of it the book already has, and what is missing, read live rather than written down. Cheapest of the three and the only one that changes nothing about what the screen is for. It also stays empty until the importer ships, so on switch day the agent still has no file list.

What I would pick, and the cost of it

One. It is the only one of the three that leaves an agent no worse off on switch day, and that is the whole reason this screen is step one rather than step four.

Two is the better screen and I would build it second, not first. It needs a column, a write path and a broker view of who has not answered, and none of that helps the switch. Building it first means the switch waits on a feature rather than on a port.

Three is honest and cheap and I would not ship it alone, because an agent opening Transactions and reading a readiness panel about SkySlope has still lost their file list. It is a good panel to put under one, where it explains why the commission column is all dots.

The cost of one is that nothing asks the agent to confirm a file is theirs, so a wrong import stays wrong until somebody notices. That risk exists today on the old Hub too, so choosing one does not add it, but it does mean it survives the move.
